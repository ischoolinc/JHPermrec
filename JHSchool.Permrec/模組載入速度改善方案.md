# JHSchool.Permrec 模組載入速度改善方案

- 日期：2026-10-21
- 分支：`fast_loading`
- 範圍：**模組啟動**，也就是 FISCA 呼叫 `Program.Main` 的這段時間。點選學生後的資料讀取不在本文件範圍內，之前兩輪的 openspec change 已經處理過。

---

## 1. 背景：FISCA 如何啟動本模組

以下是反編譯 `FISCA.dll` 的結果（`FISCA.Tasks.InitModules.Execute`、`FISCA.StartupPoint.Start`）：

- 本模組的進入點標記為 `[ApplicationMain]`。FISCA 把它歸類為 `IsFirstRequired`、優先權 `MiddleSynchronized`，**在 UI 執行緒上第一個同步執行**。
- 每個進入點都用 `Stopwatch` 計時，結果存在 `StartupPoint.StartupElapsed`。診斷模式下可在「進階工具 → 關於」查看各模組的啟動耗時。
- `ApplicationStarter` 把 `ServicePointManager.DefaultConnectionLimit` 設為 **5**，所有模組共用這 5 條連線。

因此，`Main` 裡花掉的每一毫秒都直接加在使用者等待登入完成的時間上。

---

## 2. 問題分析

### 2.1 每個資料項目在啟動時被建構 3 次（主要瓶頸）

`Program.Main` 透過 `Student.Instance.AddDetailBulider(...)` 和 `Class.Instance.AddDetailBulider(...)` 註冊資料項目。反編譯 `JHSchool.dll` 和 `FISCA.Presentation.dll` 後，呼叫過程如下：

| 順序 | 方法 | 行為 |
|---|---|---|
| 1 | `JHSchool.Student.AddDetailBulider`（以 `new` 隱藏基底方法） | 呼叫 `item.GetContent()` 讀取 `FeatureCode` 屬性並檢查權限，**產生的實例被丟棄** |
| 2 | `JHSchool.LegacyPresentBase<T>.AddDetailBulider` | 再呼叫一次 `item.GetContent()`，做相同的檢查，**產生的實例被丟棄** |
| 3 | `FISCA.Presentation…NavContentPresentation.AddDetailBulider` | 呼叫 `item.GetContent()`，加入 DetailPanel（實際使用的就是這個實例） |

`DetailBulider<T>.GetContent()` 每次都會 `new T()`。

**影響：**

- 本模組註冊了 8 個學生資料項目和 1 個班級資料項目。啟動時共建構 **27 個控制項，只用到 9 個**。
- 每次建構都會跑完整的 `InitializeComponent`，裡面是大量 DotNetBar 控制項。例如 `ParentInfoPalmerwormItem.designer.cs` 有 664 行、`AddressPalmerwormItem.designer.cs` 有 415 行。
- 被丟棄的 18 個實例沒有被 Dispose。它們在建構子裡訂閱了 `JHAddress.AfterUpdate`、`JHPhone.AfterUpdate`、`JHParent.AfterUpdate` 等靜態事件，所以會一直留在記憶體裡，之後每次資料更新也都會收到通知。

### 2.2 建構子內含啟動期間不需要的工作

因為 2.1，以下工作在啟動時都會乘以 3：

| 資料項目 | 建構子中的工作 | 問題 |
|---|---|---|
| `ParentInfoPalmerwormItem` | 欄位初始化 `private QueryHelper _Qp = new QueryHelper();` | **實測為 Main 中最大的耗時（約 600ms）。** `QueryHelper` 的建構子會呼叫 `DSAServices.DefaultDataSource.AsContract("admin")`，而 `AsContract` 每次都會 `SendRequest(ConnectService, ...)`，在 UI 執行緒上同步等待一次伺服器往返。這段發生在建構子本體之前，從建構子內部計時看不到 |
| `ParentInfoPalmerwormItem` | 啟動 4 個 BackgroundWorker（國籍、職業、學歷、關係） | 國籍的 `DoWork` 是空的，UDT 查詢 `AccessHelper.Select<UDT_NationalityMapping>()` 寫在 `RunWorkerCompleted` 裡，**等於在 UI 執行緒上連線伺服器**。另外 3 個 worker 的 `DoWork` 也都是空的，只是用來延後填入寫死的清單 |
| `AddressPalmerwormItem` | `static readonly CountyTown _CountyTown = new CountyTown()`，並啟動 county worker | 類別第一次初始化時，會在 UI 執行緒上解析郵遞區號 XML 內嵌資源 |
| 各資料項目 | 訂閱 `JH*.AfterUpdate` 靜態事件、建立 `ChangeListener` 與 BackgroundWorker | 被丟棄的實例會造成事件洩漏 |

### 2.3 啟動預載和其他模組搶連線

`Program.Main` 結尾（[Program.cs:893](Program.cs#L893)）：

```csharp
System.Threading.ThreadPool.QueueUserWorkItem(x =>
{
    JHSchool.Data.JHStudent.SelectAll();
});
```

- 它雖然在背景執行，但發生在其他模組正在同步啟動的期間，會占用 5 條共用連線中的一條，並且下載全校學生資料。
- 目的只是加速「班級資訊」（`ClassItem`）第一次開啟。但 `ClassItem` 本來就會在背景載入，使用者也不一定會打開它。

### 2.4 小項目

- `Properties.Resources.paste_64` 在 Main 裡被讀取 3 次。每次讀取 Resources 屬性都會重新解碼成新的 Bitmap。

## 3. 改善方案

### 方案 A：跳過 JHSchool 包裝層，直接註冊到底層面板（效益最大）

**做法：** 在 `Program` 裡新增輔助方法，自行檢查權限後，直接呼叫 `K12.Presentation.NLDPanels` 的 `AddDetailBulider`：

```csharp
// 直接註冊至 NLDPanel，避免 JHSchool 包裝層為檢查權限而額外建構兩次 DetailContent
private static void AddStudentDetail<T>() where T : FISCA.Presentation.DetailContent, new()
{
    if (User.Acl[typeof(T)].Viewable)
        K12.Presentation.NLDPanels.Student.AddDetailBulider(new FISCA.Presentation.DetailBulider<T>());
}

private static void AddClassDetail<T>() where T : FISCA.Presentation.DetailContent, new()
{
    if (User.Acl[typeof(T)].Viewable)
        K12.Presentation.NLDPanels.Class.AddDetailBulider(new FISCA.Presentation.DetailBulider<T>());
}
```

再把 [Program.cs:62-86](Program.cs#L62-L86) 的註冊改成呼叫上面兩個方法。

**為什麼行為不變：**

- `JHSchool.Student.Instance` 的建構方式是 `new Student(NLDPanels.Student)`，`Class.Instance` 是 `new Class(NLDPanels.Class)`。底層是同一個面板。
- 包裝層的權限判斷是 `GlobalOld.Acl[type].Viewable`，而 `Framework.User.Acl` 的實作就是 `=> GlobalOld.Acl`，兩者完全相同。
- 本模組所有資料項目都有標 `[FCode]`，所以包裝層一定會走權限判斷那條路，不會落到「沒有屬性、直接加入」的分支。

**外部 builder：** `IStudentClassDetailItemAPI.CreateBasicInfo()` 回傳的是其他模組提供的 builder。實作時發現它就是 `DetailBulider<T>`，所以可以從泛型參數取得內容型別，不必建構就能檢查權限，詳見第 6 節。

**預期效益：** 啟動時的建構次數從 27 降為 9，被丟棄實例造成的事件洩漏也一併消失。

### 方案 B：讓建構子變輕

原則是：建構子只做 `InitializeComponent` 和必要的欄位初始化。需要連線、解析資源或訂閱靜態事件的工作，延到控制項第一次 Load 或第一次 `OnPrimaryKeyChanged` 時再做。

| 檔案 | 修改內容 |
|---|---|
| `ParentInfoPalmerwormItem.cs` | 國籍 UDT 查詢移進 `DoWork`，結果存進 `static` 快取，整個工作階段只查一次。`cboNationality_TextChanged` 改為比對這份快取。職業、學歷、關係這三個空的 worker 刪除，改成在 Load 時直接用 `Utility.GetXxxList()` 填入 |
| `AddressPalmerwormItem.cs` | `CountyTown` 改成 lazy 靜態欄位，在 county worker 的 `DoWork` 裡第一次用到時才建立。county worker 延到 Load 時才啟動 |
| 各資料項目 | `JH*.AfterUpdate` 的訂閱從建構子移到 Load，並與 `Disposed` 時的取消訂閱成對 |

**注意事項：**

- `ParentInfoPalmerwormItem.cs` 是 **UTF-16 LE** 編碼，`BeforeEnrollmentItem.cs` 和 `PhonePalmerwormItem.cs` 等檔案是 **Big5（CP950）** 編碼。修改時必須保留原本的編碼。
- `DiplomaInfoPalmerworm` 的建構子裡有 `if (!string.IsNullOrEmpty(PrimaryKey)) BGWork.RunWorkerAsync();`。建構時 PrimaryKey 一定是空的，所以這行實際上不會執行，可以一併整理。

**預期效益：** 啟動期間不再在 UI 執行緒上查詢 UDT、不再解析郵遞區號 XML。和方案 A 搭配時，剩下的 9 次建構也會變輕。

### 方案 C：延後啟動預載

有兩種做法，建議採用 C1：

- **C1（建議）：** 移除 `Main` 結尾的 `ThreadPool` 預載，改成在第一次 `Student.Instance.SelectedListChanged` 時，於背景觸發一次（用旗標確保只觸發一次）。這時模組啟動已經結束，不會和其他模組搶連線，使用者打開「班級資訊」之前通常也已經載入完成。
- **C2：** 直接移除預載，完全交給 `ClassItem` 自己的背景載入。

若採用 C1，建議讓預載直接呼叫 `ClassItem` 的靜態載入方法，用 lock 保護。這樣同時填好 `_AllClassRecs` 和 `_AllStudRecList`，避免預載和 `ClassItem.BGWork_DoWork` 同時呼叫 `SelectAll`。K12.Data 的 `EntityCache<T>` 繼承自普通的 `Dictionary`，沒有執行緒保護，同時寫入可能出錯。

### 方案 D：小項目

- `Properties.Resources.paste_64` 改成讀取一次，存在區域變數後重複使用。

## 4. 建議實施順序

| 順序 | 方案 | 風險 | 修改範圍 |
|---|---|---|---|
| 1 | A：直接註冊到 NLDPanel | 低 | `Program.cs` |
| 2 | C：延後啟動預載 | 低 | `Program.cs`、`ClassItem.cs` |
| 3 | B：建構子變輕 | 中（UTF-16 和 Big5 編碼、需要逐一回歸測試） | 各 `StudentExtendControls/*.cs` |
| 4 | D：資源只讀一次 | 極低 | `Program.cs` |

## 5. 驗證方式

### 5.1 量測

1. 改動前，用 FISCA 診斷模式啟動，在「進階工具 → 關於」記下 JHSchool.Permrec 的啟動耗時（單位毫秒）。
2. 也可以暫時在 `Main` 裡加 `Stopwatch` 分段計時：資料項目註冊、Ribbon 設定、權限註冊、ListPane 欄位，各自輸出到 `RTOut.WriteLine`。
3. 每完成一個方案就重新量測，記錄差異。

### 5.2 功能回歸

- **權限：** 用沒有各資料項目檢視權限的角色登入，確認對應的資料項目不會出現（驗證方案 A 的權限判斷和原本一致）。
- **資料項目順序：** 學生、班級的資料項目顯示順序和改動前相同。
- **家長資料：** 國籍下拉選單有內容；輸入不在對照表裡的國籍時，會出現警示。
- **地址資料：** 縣市、鄉鎮下拉選單和郵遞區號帶入功能正常。
- **班級資訊：** 第一次開啟時，班級和座號清單正確；儲存後清單會更新。
- **事件：** 在其他模組修改學生地址或電話後，目前顯示的資料項目會自動重新載入。

## 6. 實作狀態（2026-10-21）

| 方案 | 狀態 | 修改內容 |
|---|---|---|
| A | 已完成 | `Program.cs` 新增 `AddStudentDetail<T>()`、`AddClassDetail<T>()`，本模組的資料項目改用這兩個方法註冊。`IStudentClassDetailItemAPI` 提供的外部 builder 改用 `AddStudentDetail(IDetailBulider)`：如果它是 `DetailBulider<T>`，就用反射取得內容型別，不必建構就能檢查權限，判斷條件和包裝層相同（`Framework.Security.FeatureCodeAttribute` 加上 `GlobalOld.Acl`）；無法判斷型別時，仍交給包裝層處理 |
| B | 部分完成 | 見下方說明 |
| C | 已完成（C1） | 移除 `Main` 結尾的預載，改成第一次 `Student.Instance.SelectedListChanged` 時才在背景觸發一次。`ClassItem` 新增 `internal static EnsureCacheLoaded()`，用 lock 保護，預載和 `BGWork_DoWork` 共用 |
| D | 已完成 | `paste_64` 只讀一次 |

**方案 B 已完成：**

- `ParentInfoPalmerwormItem.cs`：
  - `_Qp`（`QueryHelper`）改成第一次使用時才建立。實際使用的地方只有兩處：背景 `DoWork` 讀取延伸資料，以及儲存。
  - 國籍 UDT 查詢移到 `DoWork`，結果存進靜態快取 `GetNationalityNames()`。
  - `cboNationality_TextChanged` 改為比對快取，打字時不再查詢 UDT。
  - 職業、學歷、稱謂三個空的 worker 移除，改成在建構子裡直接呼叫 `FillJobList()`、`FillEduDegreeList()`、`FillRelationshipList()`。
  - 檔案維持 UTF-16 LE（含 BOM）、CRLF。
- `AddressPalmerwormItem.cs`：`CountyTown` 改用 `Lazy<CountyTown>`，第一次在 county worker 的背景執行緒取用時才解析 XML。

**方案 B 刻意未做：**

- **事件訂閱移到 Load：** 方案 A 完成後，已經沒有被丟棄的實例，事件洩漏的問題消失。剩下的實例本來就需要訂閱這些事件，而訂閱本身的成本可以忽略。這項修改還要動到多個 Big5 編碼的檔案，風險大於效益。
- **整理 `DiplomaInfoPalmerworm` 建構子中不會執行的 `RunWorkerAsync`：** 不影響效能，而且檔案是 Big5 編碼，暫不修改。

**行為差異：**

- 國籍對照表在整個工作階段只查一次。如果使用者在「教務作業 → 國籍中英文對照表」新增國籍，國籍輸入檢查要等重新登入後才會反映新資料。
  - 改動前，下拉選單本來就只在建構時載入一次，所以下拉選單的行為沒有改變；只有輸入檢查從「每次即時查詢」變成「使用快取」。

**量測結果（Release 版，用暫時性 `Stopwatch` 量測 `Main`，量測程式碼已移除）：**

第一版實作完成後，使用者回報「關於」裡的毫秒數反而變長。為了找出原因，我在 Main 裡分段計時，結果如下：

| 段落 | 第一版實作 | 加入 `QueryHelper` 延遲建立、外部 builder 直接註冊後 |
|---|---|---|
| 註冊 `ParentInfoPalmerwormItem` | 672ms（建構子本體只有 69ms） | 69ms |
| 註冊外部班級資訊（`StudentClassItem_KH`） | 355ms | 4ms |
| 其餘資料項目合計 | 約 75ms | 約 75ms |
| **`Main` 總耗時** | **1135ms** | **188ms** |

- 國籍 UDT 查詢約需 2–3 秒，但已經在背景執行緒上，不計入 `Main`。
- 改動前版本（HEAD 編出的 Release 版）在「關於」裡的毫秒數**沒有留下紀錄**，所以目前無法列出相對於改動前的確切改善幅度。
- 使用者已確認外部班級資訊在新版中仍正常顯示。

**驗證：**

- `MSBuild`（Release）編譯成功。
- 第 5.2 節的其他功能回歸項目尚未逐項執行。

## 7. 附帶發現（與速度無關，建議另案確認）

- **（更正）`DiscoverAPI` 的時序：** 先前推測本模組以 `[ApplicationMain]` 最早啟動，所以 `DiscoverAPI<IStudentClassDetailItemAPI>()` 會回傳 null。實測結果是**有找到**，由 `StudentClassItem_KH`（`StudentClassItemContent`）提供，因此「班級資訊」的覆寫是有效的，原本的推測不成立。
- **權限代碼與名稱：** `RoleAclSource` 中 `JHSchool.EduAdmin.Ribbon00801` 的顯示名稱是「產生異業證書字號」，看起來是「產生畢業證書字號」的錯字。
